# failure_modes.md — 基础 Agent 典型失败模式与本 Skill 的对策

评测对照组是"不加载 Skill 的基础 Agent"。以下是它在引用插入任务上的高频失败，
每条给出本 Skill 的结构性对策（规则在引擎层强制执行，不依赖模型自觉）。

## 1. 整段末尾集中堆放引用

- **现象**：一段 4 个论断句，基础 Agent 在段末一次性挂 `[1-5]`，读者无法知道哪句对应哪条。
- **危害**：引用失去溯源功能；评审视为主力缺陷。
- **对策**：decisions 以**句子**为单位定位；引擎插在论断句末（终结标点之前）；
  `placement_audit.json` 用"标记在段末 30 字符内而论断句在段中部"规则双向审计
  （`pre_existing_end_of_paragraph_dumping_observed` + `post_insertion_misplacement_suspects`）。

## 2. 正文编号与参考文献表不同步

- **现象**：基础 Agent 手写正文 `[3]`，又手写文献表 `[3] 张三……`，增删一处后两边错位；
  或正文出现 `[7]` 而文献表只有 5 条（悬空编号），或编号 1..N 中间有缺口。
- **对策**：Agent 全程不碰数字；引擎按首次出现顺序统一分配 1..N，references.md 用同一
  `citation_order.json` 渲染；`validate_output.py` 强制复检 `references.json` 编号连续性，
  可选 `cite_engine.py audit` 复查悬空/缺口。

## 3. 给作者自己的新结果加引用

- **现象**："本文样品循环 200 次容量保持 92%[6]。"——把自己的数据挂到别人文献上，
  既是学术不规范也制造了虚假溯源。
- **对策**：`claim_rubric.md` 第二节明确"不需要引用"清单（作者新结果/公知常识/过渡句），
  并配 10 条正反例训练判断；Phase 3 只给命中的论断句写 decision。

## 4. 一句多引写成相邻标记或拆开多句

- **现象**：`…失效[2][3]。`（两个标记并列）或把共同支撑一句的两条文献拆到两句末尾。
- **对策**：引擎把同句同位置的 decisions 合并为单标记 `[2-3]`（连续区间自动压缩），
  审计项 `no_adjacent_brackets` 校验。

## 5. 定位靠"感觉"，插错句子

- **现象**：模型凭记忆复述原句，复述得不对就插到了错误的句子后面，或干脆插在段落开头/结尾。
- **对策**：引擎三级定位（精确→空白宽容→去空白映射），全部失败即记 `exceptions.json`
  **并跳过**（`skipped_no_fabrication`）——宁可不插，不可插错；Agent 可据 exception 修正
  sentence 后重跑。

## 6. 引用形式与任务书不一致 / 一文两制

- **现象**：task.md 要求顺序编码制，Agent 却混用 `(Smith, 2020)` 与 `[1]`；或前半 numeric 后半 author-year。
- **对策**：形式决策集中在 Phase 1（task.md 优先，冲突记 change_log）；`--form auto` 由
  `--style` 统一推断，引擎保证全文单一形式。

## 7. 文献表包含从未被引用的条目 / 漏掉被引条目

- **现象**：把库里 20 条全列进文献表，或正文引了的条目文献表里缺。
- **对策**：references.md 只按 `citation_order.json`（= 正文实际引用集合）渲染；
  未引用库条目如需说明，放报告而非文献表。

## 8. 臆造文献或元数据凑数

- **现象**：库中只有 5 条，Agent 编出第 6 条"看起来合理"的文献补引用。
- **对策**：红线 1；`entry_ids` 不在 `library.json` 即被引擎丢弃并记 exception，
  引擎没有"新建条目"的代码路径。
